## Zusammenfassung

Security and privacy lens, round 1 of job 004 (73e9ae52d..dcae95345). No earlier reviews exist under scratchpads/factory/004-escalation-before-recount/reviews/. I compared the edited workflow with the base copy. The escalation reordering is stricter than the base: notes now become ESCALATE when the round is fixed, pronounced or recounted, and never APPROVE. The founderLabel kind adds a record requirement where the base counted a met criterion as code, so it is also stricter. Making recount a boolean, adding Deliverfile and Pluginfile to SENSITIVE, adding the token note, and reading the spec at the head SHA (head is a validated SHA and jobDir a validated slug, so the git command cannot be injected) all tighten or pin behaviour. None of the removed selftest mutations takes away a security check without a replacement.

I found three majors:
(1) The new name filter assumes that git never prints C1, bidi or zero-width characters unquoted with core.quotePath=false. That assumption is false. I checked it: `git -c core.quotePath=false ls-files` prints U+2013 raw, and SKILL.md:120 relies on the same behaviour for umlauts. So a real file with a disguised name in the range gets RERUN on every call. That RERUN comes before the lock check and the token note, and it never escalates.
(2) The new pre-push token check in SKILL.md uses git log's default history simplification. I tested this in a throwaway repo in the scratchpad: the token file was added and then removed on a side branch, and the branch was merged. The check printed nothing, while `--full-history` showed both commits and `rev-list --objects` still listed the blob that would be pushed.
(3) The token-rotation note is dropped when the rework cap is reached, although criterion 7 requires it unconditionally.

Minors: the Gemfile is missing from SENSITIVE even though the Pluginfile rationale points at it, U+061C and some other invisible characters are not covered, and a [FOUNDER] tag now counts only at the start of a bullet.

## Befunde

1. **major** `.claude/workflows/echoel-factory-review.js`:276 — The comment at lines 274-275 says git prints none of the newly rejected characters unquoted with core.quotePath=false. That is false. git quotes only C0, DEL, '"' and '\'; with quotePath=false it prints every byte >= 0x80 verbatim. Measured: `git -c core.quotePath=false ls-files` prints `reports/Astra – Hardware, Klang und Design (2026-10-15).md` with U+2013 raw, and SKILL.md:120 already relies on this ('ohne Oktal-Escapes passt ein Name mit Umlaut noch auf sein Präfix'). U+0085, U+200B-200F, U+2028-202E, U+2060-2069 and U+FEFF are all multibyte UTF-8 with bytes >= 0x80, so a lens that copies git faithfully returns them as they are. Failure: a commit in the range adds a file whose name carries U+202E or U+200B (a Trojan-Source-style disguised name, for example under .claude/hooks/, or next to a committed .claude/settings.local.json). Every lens reports it exactly as printed, `garbled` lists every lens, and line 277 returns RERUN before `lockChanged` (line 293) and `fixed` (line 376) are computed. Every re-call sees the same git output, so the round reruns forever: it never escalates and never adds the token note, and SKILL.md:121-122 tells the PM it is a lens fault. In the base, a faithful listing could not trigger this RERUN (git escapes C0/DEL inside quotes), so the diff introduces a RERUN loop that repository content can trigger. That contradicts the job's own Assumption that a RERUN re-calls a round nothing holds still.
   - Vorschlag: Correct the comment. When every lens that returned a list reports the same such name, treat it as a real name and ESCALATE, passing the name through ascii() in the reason, instead of RERUN. At minimum, compute lockChanged on the unquoted names before this exit and let a lock change escalate. Keep RERUN only for a name that not every lens reports. Add a selftest case in which all lenses report the same bidi or zero-width name.
2. **major** `.claude/skills/factory/SKILL.md`:74 — The new pre-push token check `git log --oneline origin/<branch>..HEAD -- .claude/settings.local.json` uses default history simplification. That mode prunes a merged side branch whose final state for the path matches the first parent. This is exactly the case the sentence names ('ein Commit, der sie auch nur kurz trug'). Measured in a throwaway repo under the session scratchpad: a side branch adds the file with a token, then removes it, and is merged. The default command prints nothing. `--full-history` prints both commits ('add token', 'remove token'). `git rev-list --objects origin..HEAD | grep -c settings.local.json` returns 1, so the push still publishes the token blob while the check reads clean. The check fails in the reassuring direction.
   - Vorschlag: Use `git log --full-history --oneline origin/<branch>..HEAD -- .claude/settings.local.json` (also `origin/main..HEAD` for a new branch), or check `git rev-list --objects origin/<branch>..HEAD | grep -F .claude/settings.local.json`.
3. **major** `.claude/workflows/echoel-factory-review.js`:376 — `fixed` is `capReached ? <cap sentence> : lockChanged.length ? <lock sentence + tokenNote> : ''`, so the token note only goes with the lock branch. In round 3 with open findings (capReached), a range that commits .claude/settings.local.json escalates with only 'rework cap of 2 reached with N open finding(s)'. The reason mentions neither the lock nor 'rotate it and remove the commit from the history'. Criterion 7 requires the note whenever .claude/settings.local.json changes. The reason is the founder-facing text routed to FOUNDER_INBOX, so a committed token can escalate without the rotation instruction. No selftest case combines the cap with settings.local.json.
   - Vorschlag: Build `fixed` from independent parts: the cap sentence if capReached, the lock sentence if lockChanged.length, and tokenNote whenever lockChanged includes .claude/settings.local.json, joined with '; '. Add a selftest case: round 3, an open major, a lens that sees .claude/settings.local.json, and the reason must contain 'rotate it'.
4. **minor** `.claude/workflows/echoel-factory-review.js`:225 — Pluginfile was added to SENSITIVE as the file defining 'gems that run in the signing lane with the App Store Connect key' (spec Assumption 6). By its own header it is inert: the Gemfile has no plugins_path eval, and CI installs fastlane directly (`gem install fastlane:2.225.0` in .github/workflows/testflight.yml:349 and studio-testflight.yml:105). The root `Gemfile` is the file that would activate it, and it is not in SENSITIVE. An out-of-scope change to the Gemfile would therefore not be flagged as not covered, while the inert file is.
   - Vorschlag: Add /^Gemfile(\.lock)?$/ to SENSITIVE, the SKILL.md list and the selftest OUTSIDE list. Correct the spec's rationale for Pluginfile, which is inert today.
5. **minor** `.claude/workflows/echoel-factory-review.js`:276 — Criterion 6 names bidi and zero-width characters, but the class misses U+061C ARABIC LETTER MARK, one of the nine Unicode Bidi_Control code points.
