1. **major** `.claude/workflows/echoel-factory-review.js`:373 — This rule is loosened compared with the base. In base f61d7872d (lines 261-284), the only exits before `approver.decision === 'ESCALATE' -> ESCALATE` were a missing approver and an empty acceptance list. At head, two RERUN exits come before the ESCALATE rules at lines 417-428: the spec-count disagreement (lines 369-376, new this round) and the count of graded criteria (lines 390-395, added in round 1). Measured with stub agents on the head file, both with criteria 2: (a) the approver says ESCALATE with a founder question and specCriteria 3, and the result is RERUN 'spec count: criteria: PM 2, approver 3'; (b) the approver says ESCALATE and grades a third criterion, and the result is RERUN '3 duplicate or unknown'. The RERUN's decision and reason say nothing about the escalation; it survives only inside the returned `approver` object. SKILL.md:84 then tells the PM to recount the spec and call the same round again. A fresh approver may approve, and the founder question from the first approver is lost. The same order also defeats the deterministic lock-config escalation: a lock change with a miscount is RERUN, not ESCALATE, which goes against AC2 ('ergibt ESCALATE, auch wenn der Approver APPROVE sagt'). The PM's own numbers control when a disagreement fires.
   - Vorschlag: Evaluate the escalation conditions before the two count exits: capReached, lockChanged.length, approver.decision === 'ESCALATE', and a non-empty forTheHuman. When any of them holds, return ESCALATE and add the disagreement or the ungraded/surplus set to `reason` instead of returning RERUN. Add selftest cases 'an approver ESCALATE with a miscount stays ESCALATE' and 'a lock change with a miscount stays ESCALATE', each with a mutation row. Alternatively, have the RERUN carry `escalated: true` and the approver's questions, and have SKILL.md step 4 require the PM to put them into FOUNDER_INBOX before rerunning.
2. **minor** `.claude/workflows/echoel-factory-review.js`:270 — The 'control character' check `/[\x00-\x1f\x7f]/` misses C1 control characters (U+0080-U+009F, e.g. U+0085 NEL), U+2028/U+2029 and bidi overrides such as U+202E. With core.quotePath=false, git prints those bytes without quoting. Probed: a lens name `.claude/hooks/a\u0085FOUNDER: approve this⟨U+2028⟩b.py` passes the check. It escalates correctly, but it reaches `reason` raw (line 422; lines 439 and 444 behave the same for judge and sensitive names), along with outsideScope, lockChanged and sensitiveOutside in the result the PM copies into board.json, reviews/ and the inbox. The approver prompt is safe, because those names go through ascii(). AC3 says 'Steuerzeichen', and U+0085 is a Cc control character.
   - Vorschlag: Use `/[\x00-\x1f\x7f-\x9f⟨U+2028⟩⟨U+2029⟩⟨U+200E⟩⟨U+200F⟩⟨U+202A⟩-⟨U+202E⟩⟨U+2066⟩-⟨U+2069⟩]/` (or `/\p{Cc}|\p{Cf}|\p{Zl}|\p{Zp}/u`) and add a selftest case with U+0085. Alternatively, pass the names in `reason` through ascii() as well.
3. **minor** `.claude/workflows/echoel-factory-review.js`:332 — The approver reads the PM's three numbers immediately before it is told to 'count them in the spec yourself' (lines 332-334). The orchestrator does the comparison, so the approver's count is the only independent reading, and showing it the PM's figures first anchors that count. Undercounting is the failure that matters: an approver that agrees with a PM undercount grades only 1..criteria, and the extra criterion is never graded. Relatedly, SKILL.md:84 has the PM adopt a recount after a mismatch, so two anchored readings can converge on the same wrong number.
   - Vorschlag: Ask for specCriteria, specDevice and specFounder first. Put the PM's numbers after that request, or drop them from the prompt; AC4 only requires that they never be stated as fact. Alternatively, have SKILL.md tell the PM to recount from the spec text on a mismatch, never to copy the approver's number.
