Paths: a new package name always comes from ProjectLibrary.fileName(for:), which turns / \ : ? % * | " < >, newlines and Cc/Cf characters into dashes and trims leading and trailing dots. A name like "..", "a/../b", ".hidden" or one with an RTL override therefore cannot leave the library folder, cannot become a hidden file and cannot spoof its extension. The ".echoel" extension is always appended, so a rename cannot land on the system Inbox folder either. ProjectLibrary.rename refuses a package whose parent, with symlinks resolved, is not the library directory (lines 158-161). FileManager.moveItem never overwrites, so a race with the off-main earlier-songs import cannot clobber a song: reservePackage uses an exclusive createDirectory, and rename moves on to the next free name when the target exists (lines 179-184). isSameItem uses lstat-style attributes, so a symlink cannot pass as the package. The case-only in-between name is built from the package's own stem plus a UUID prefix, stays inside the directory, and is visible in the Open list rather than hidden. Untrusted input: a foreign song opened from Files or AirDrop moves nothing by itself. SongFileName.opened records its inner name, so only a user rename (or its Undo/Redo) moves the package. Undo history is cleared on open (ProjectStore.open), so an Undo cannot rename another song. The only caller of renameSong is the RenameSongView door. The on-device assistant's tool list (AgentSession.swift:185) has no project-rename tool, so model text cannot move a package. The name is still validated by Names.validated inside Command.apply. Nothing new leaves the device: shares and exports are temp copies made while isExporting holds the package, and the busy set (import, export/share, media load, take) covers every task that reads or writes inside the package. Two minor points below; no blocker or major.

## Befunde

1. **minor** · `EchoelStudio/Core/Sources/EchoelCore/ProjectLibrary.swift`:174
   - Befund: Case-only rename: when the second move (between -> target) fails, the rollback is `try? files.moveItem(at: between, to: url)` and its failure is thrown away. If the rollback also fails, the song's document and its Media/ folder stay under the in-between name. DocumentController.followRenamedSong (line 617) keeps currentURL at the old path and has already called fileName.followed, so it will not retry. The next saveNow then runs library.write (createDirectory plus project.json) at the old path, which creates a document-only package with no Media. The user's audio is then split from the song that references it. This needs two consecutive move failures in the same instant, so it is unlikely, but the integrity cost is silent.
   - Vorschlag: When the rollback fails, report where the package now is (for example throw an error that carries `between`, or return `between`). Have followRenamedSong set currentURL to that location instead of leaving it at a path that no longer holds the song.
