## Befunde

### 1. major — `EchoelStudio/App/Views/AboutView.swift`:22

A visible privacy sentence is now contradicted by the diff's design. About → 'Your data' says: 'Echoel uses the network only for the App Store, when you open the store, and for Network MIDI, when you turn it on.' The diff adds `await self?.refreshOwned()` to StoreController.init (StoreController.swift:22), and EchoelStudioApp.swift:11 constructs StoreController at launch. So every launch now asks StoreKit for the purchase state, whether or not the store is ever opened. The spec says why in plain words: 'Die App prüft beim Start (nicht erst, wenn der Store geöffnet wird), damit ein Kauf von einem anderen Gerät ohne Store-Besuch ankommt'. Getting App Store data at launch without a store visit is exactly what the sentence's qualifier 'when you open the store' excludes. Whether StoreKit's daemon sends bytes for this particular read is UNMEASURED from this repo. A sentence in 'Your data' has to stay true either way, and today it is true only if that implementation detail breaks our way. The pre-existing Transaction.updates listener at launch already made the sentence shaky; this diff turns it into the stated design. The same claim has two pipeline twins that must move in the same commit (#456): SECURITY.md:4 ('the only network use today is the App Store, which the app asks for prices when you open the store screen') and docs/roadmap.html:96 ('this build contacts the App Store when you open the store screen').

**Vorschlag:** Reword to something true under any StoreKit behaviour, for example: 'Echoel uses the network only for the App Store — to check at launch whether you bought Echoel Plugins, and for prices when you open the store — and for Network MIDI, when you turn it on.' Apply the same correction to SECURITY.md:4 and docs/roadmap.html:96, and to the RELEASE device-list line '"Your data" names the App Store (when you open the store)' at the next bump.

### 2. major — `EchoelStudio/project.yml`:96

The new comment states as fact what the spec marks as not guaranteed: 'A group the profile lacks fails signing in studio-testflight.yml, so a mismatch never reaches a device.' Its twin in EchoelStudio/Support/Plugins/EchoelPlugins.entitlements:8-9 says 'if it ever does not, studio-testflight.yml fails at signing and uploads nothing.' Spec Assumption 2 says the opposite: 'Das ist nicht garantiert: die Alt-App-Erweiterung signierte mit einer Gruppe, die ihre App-ID nicht trug, und scheiterte erst im Host mit -3000'. The repo carries that history in EchoelmusicAUv3.entitlements and in TheAUv3RegistersAndStaysIsolatedTests claim 2: the extension registered, hosts listed it, and instantiation returned -3000 everywhere. F17 measured a signing failure only for the APP target's entitlements. This diff leaves the extension's mismatch mode unmeasured. Acceptance criterion 6 exists because the group in the extension is the first suspect for a -3000. These comments tell whoever reads them in the code that this failure cannot reach a device, which points the triage away from the one key to remove. CLAUDE.md calls a wrong-reason comment the most expensive kind, because the next session cannot disprove it.

**Vorschlag:** Keep the hedge the spec wrote. For example: 'A group the profile lacks has failed signing in studio-testflight.yml (F17, app target); for the extension that is not guaranteed — the legacy AUv3 signed with an ungranted group and failed only in the host with -3000. If Echoel Synth/Drums/EQ return -3000 in AUM, remove this key first (factory job 002, criterion 6).' Apply the same wording to the EchoelPlugins.entitlements comment.

### 3. minor — `EchoelStudio/Plugins/Shared/PluginControlsView.swift`:104

No visible sentence tells a buyer the new precondition for an unlock in a host: the Echoel app must have run on this device since the purchase. That is the only way the record gets written. Without it, the plugin falls back to StoreKit in the extension, which the spec says Apple does not support. A buyer on a second device, or one who installed and went straight to AUM, hears the demo gaps and reads 'until Echoel Synth is unlocked in the Echoel app', even though they already bought it. The StoreController doc comment (StoreController.swift:7, 'every host on every device of the same Apple account') states the same precondition-free promise in prose. The problem is latent while the copy still says 'The unlock is not on sale yet' (E8).

**Vorschlag:** When the product goes on sale, extend the locked-state line with the remedy. For example: '… until Echoel Synth is unlocked in the Echoel app. Bought it already? Open Echoel once on this device, then reload the plugin.' Also qualify the StoreController doc comment with 'once the app has run on that device'.

### 4. minor — `EchoelStudio/App/Store/StoreController.swift`:85

From the paying user's side: `PluginUnlock.recordOwned(found)` writes false after any pass that finds nothing, including the new unconditional pass at launch (line 22). One empty pass therefore overwrites an earlier true: App Store signed out, a new device not yet synced, a Family Sharing change. The extension then depends on the in-extension StoreKit fallback the spec calls unsupported, so a buyer can be sent back into the 28/30 s demo pause in a host until a later launch finds the entitlement again. The spec sanctions this ('nicht gefunden oder widerrufen → false'), so it is not a defect against the spec. It is a user-harm edge to weigh, and it is invisible to the user.

**Vorschlag:** Optional: downgrade the record only on an observed revocation (transaction.revocationDate != nil) or an explicit Restore, not on a merely empty pass. Or keep the design and add 'buyer stays unlocked after an offline or signed-out launch' to the device checks next to criteria 7 and 8.
