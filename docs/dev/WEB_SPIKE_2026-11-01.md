# Echoel im Browser — Messung vom 2026-11-01 (Spike, nichts ausgeliefert)

**Frage (Founder 2026-11-01):** „Da adaptive Web Apps in Zukunft Usus sind, will ich selbst
Echoelmusic als Browser sehen und vermarkten" — Latenz und Umsetzung für Meetings, Jams und
Liveshows, offene Formate, Sicherheit.

**Antwort, gemessen:** Echoel Studios Klang-Kern läuft als WebAssembly. Das Instrument bleibt
vorerst die App, weil der Browser auf dem iPhone zentrale Teile nicht kann (§3). Dieser Text ist
eine Messung, kein Plan und keine Behauptung nach außen: nichts davon ist ausgeliefert, und
`ContentPipeline/CLAIMS.md` bleibt die einzige Quelle für Werbesätze. Vorgeschichte: Eintrag K7
in `docs/dev/HISTORY_ARCHIVE.md` (Web/WASM, damals ohne einen einzigen Build-Lauf).

## 1. Was gemessen wurde

Werkzeug: das offizielle Swift 6.2.4 für Linux plus das passende „Swift SDK for WebAssembly"
von swift.org (`swift-6.2.4-RELEASE_wasm`, Prüfsumme aus `swift.org/api/v1/install/releases.json`),
gebaut mit `swift build -c release --swift-sdk swift-6.2.4-RELEASE_wasm`, ausgeführt unter Node 22
(`node:wasi`). Stand des Codes: `d10525c0b`. Im Repo wurde nichts verändert.

| Paket | Ergebnis für wasm32-wasi |
|---|---|
| `EchoelStudio/DSP` (44 Dateien) | baut unverändert, 0 Fehler, 0 Warnungen; Tests 302 von 302 grün |
| `EchoelStudio/Core` | braucht zwei kleine Änderungen (§4); danach Tests 595 von 614 grün — die 12 roten sind Dateisystem-Tests (WASI kann keine Dateien atomar schreiben), 7 liefen wegen Laufzeit-Grenzen von Node nicht |
| `EchoelStudio/Engine` (Kernels + Engine) | baut, 1 Warnung; rendert einen ganzen Song („Four Tracks" mit Akkord-Clip und Bass über `OfflineRender`) |
| `EchoelHost` (AVFoundation, Audio Units) | nicht Teil der Messung — gibt es im Browser nicht |

**Tempo:** der wasm-Kern rendert 70- bis 140-mal schneller als Echtzeit (nativ unter Linux 100- bis
200-mal). Pro 128-Sample-Block (das feste Maß eines AudioWorklets, 2,67 ms) braucht er höchstens
1,5 % der verfügbaren Zeit. Gemessen in einer VM mit 2 Kernen, offline, eher zu pessimistisch.

**Klang:** numerisch gleich, nicht bitgleich. Die größte Abweichung zum Linux-Build liegt bei
−136 dBFS (Signal zu Differenz 141 dB); im 16-Bit-Export unterscheiden sich wenige Samples um
1 LSB. Ursache gemessen: die Mathebibliotheken (glibc gegen wasi-libc) runden bei `sinf`, `tanf`,
`log10f`, `tanhf`, `exp`, `sin`, `cos` das letzte Bit anders. Innerhalb von wasm ist jeder Lauf
gleich.

**Größe — das eigentliche Hindernis:** Foundation zieht 36 MB Sprachdaten (ICU) in die Datei.

| Variante | gestrippt | gzip | Laden in Node |
|---|---|---|---|
| DSP mit Foundation | 52,5 MB | 18,8 MB | 130–190 ms |
| DSP ohne Foundation (Spike-Kopie) | 6,4 MB | 1,9 MB | 35–50 ms |

Die Foundation-freie Kopie klingt bitgleich zur Foundation-Fassung (960.000 von 960.000 Samples).

## 2. Was für hörbares Spielen im Browser fehlt (nicht gebaut)

Die Brücke, nicht der Kern: ein wasm-Modul mit einer exportierten `render(frames)`-Funktion statt
`main()`; ein AudioWorkletProcessor, der sie je 128er-Block ruft; ein kleiner JS-Ersatz für die
WASI-Aufrufe; ein Foundation-freier Build des DSP. Steuerung aus der Oberfläche über
`port.postMessage` mit Parameter-Momentaufnahmen; wer die lock-freien Ringpuffer echt teilen will,
braucht SharedArrayBuffer (COOP/COEP-Header) und ein SDK mit Threads (`wasip1-threads`) — das
offizielle 6.2.4-Paket hat nur `wasm32-unknown-wasip1`. Sampler und Audiodateien bräuchten
`decodeAudioData` (ANNAHME, nicht getestet).

## 3. Was der Browser auf dem iPhone nicht kann (Stand 2026-11-01)

- **MIDI:** Safari unterstützt die Web-MIDI-API in keiner Version, weder iOS noch macOS
  (caniuse.com/webmidi). Außerhalb der EU nutzen alle iPhone-Browser Safaris Technik. Chrome,
  Edge und Firefox auf dem Desktop können MIDI.
- **Audio Units (AUv3):** gibt es im Browser nicht.
- **Kamera mit Blitz** (Puls über den Finger): geht inzwischen auch in Safari (WebKit-Bug 243075,
  gelöst; auf iOS 17.5.1 berichtet).
- **Latenz-Physik für Jams übers Netz:** eng zusammen spielen geht bis etwa 20 ms Laufzeit pro
  Richtung (Stanford, Chafe: San Francisco–Denver); längere Verzögerung bremst das Tempo. Darüber
  hinaus trägt nur „einen Takt versetzt": jeder hört die anderen genau einen Takt später, im Takt —
  das geht auch im Browser. Für das Publikum einer Liveshow sind Sekunden Verzögerung belanglos.

## 4. Die zwei Stellen in Core, die WebAssembly braucht (nicht geändert)

1. `.atomic` beim Schreiben (`ProjectLibrary.swift`, `DiagnosticLog.swift`): unter WASI nicht
   verfügbar → eine Schreib-Option je Plattform (`#if os(WASI)`).
2. `Media.swift`: eine Konstante `46_080_000 * 60` läuft auf wasm32 über, weil `Int` dort 32 Bit
   hat → die Frame-Zahl als `Int64`. ANNAHME, ungeprüft: weitere 32-Bit-Stellen wie
   `Project.decodedBytes` könnten ab etwa 268 Mio. Frames überlaufen.

Beides ist auf iPhone und Mac (64 Bit) KEIN Fehler; es gehört in die erste Web-Scheibe, nicht davor.

## 5. Empfehlung

Die App bleibt das Instrument (Latenz, MIDI, Audio Units, Kamera, offline). Der Browser wird das
offene Fenster dazu — mit DEMSELBEN Swift-Kern, zweimal übersetzt, nie ein zweiter Klang:
zuhören und mitsehen (Liveshow, Song im offenen Format abspielen), One Clock, Jam-Gäste auf dem
Desktop. Sicherheit wie in der App: kein Konto, kein eigener Server nötig, jede Verbindung aus bis
man sie einschaltet, Körperwerte nie ohne Zustimmung; im Browser zusätzlich WebRTC (immer
verschlüsselt). `docs/dev/FOUNDER_PRODUCT_LAW.md` §4b gilt auch hier.

Reihenfolge: erst die Geräte-Session der App (Entscheidung 2026-11-01: keine neue Welle davor),
dann als erste Web-Scheibe der Beweis „ein Song im offenen Format spielt hörbar in Chrome und
Safari" (Foundation-freier DSP + AudioWorklet-Brücke). Werben erst, wenn das läuft.

## 6. Reproduzieren

`swift sdk install <URL des 6.2.4-wasm-Pakets von swift.org> --checksum <aus releases.json>`,
dann `swift build -c release --swift-sdk swift-6.2.4-RELEASE_wasm --package-path EchoelStudio/DSP`.
Für Core vorher die zwei Änderungen aus §4. Async-Tests im Debug-Build brauchen einen größeren
wasm-Stack (`-Xlinker -z -Xlinker stack-size=8388608`).
